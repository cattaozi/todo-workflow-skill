# skills/solution —— 我怎么制定可落地的方案

> 方案设计把已经基本明确的问题，转化为边界清楚、异常闭环、可实施且可验收的决策基线。它沉淀的是补盲和闭环机制，不是固定章节或长文模板。

## 方案模型

- **方案对象**：一个已有相对明确目标，但实现路径、边界或关键取舍尚未收敛的工程问题。
- **决策基线**：用户已拍板、后续实施必须遵守的选择和不变量。
- **认知台账**：已验证事实、用户已决策、方案建议、暂定假设和待确认问题。
- **不变量**：不依赖某次请求或实现细节的可判定约束，后续应落到数据、状态、接口、权限或验收证据。
- **差距**：当前系统与目标方案之间需要直接复用、扩展、新增、停用或外部补齐的部分。
- **上线闸门**：进入某个实施或生产阶段前必须已经具备的证据、决策或外部条件。

## 处理入口

先按用户的实际意图、当前对象的成熟度和下一步目标判断，不根据“方案”“设计”等字面触发。

1. **问题还不清楚**：需要验证价值、查明事实或比较方向时，回到 `skills/explore.md`；产品目标、范围或用户问题未定时，回到 `skills/prd.md`。
2. **需要制定方案**：目标已基本明确，需要建立技术路径、边界、不变量、失败恢复和实施基线时，进入本能力。
3. **已有方案需要挑战**：用户要求找风险、审视前提或提供独立判断时，进入 `skills/review.md`；Review 可以将建议回流到方案，但不自动改变已拍板决策。
4. **方案已定需要实施**：已能形成目标状态、范围、任务级规格和 AC 时，按 `skills/todo.md` 进入 TODO / Epic；方案文档不代替任务级实施规格。
5. **简单局部改动**：单模块、低风险、易回滚且实现路径清楚时，直接给轻量实施计划，不为了仪式感生成独立方案。

## 深度判断

方案深度由返工代价、边界数量、状态复杂度、外部副作用和安全风险共同决定，不由文档字数决定。

### 轻量方案

适用于边界清楚、状态简单、可快速回滚的局部变更。通常只需说清问题、选择、影响、改动范围和验收。

### 标准方案

适用于跨模块、有持久状态、兼容性或生命周期问题的变更。需要说清边界、事实所有权、不变量、正常与失败流程、差距和分阶段实施。

### 高风险方案

适用于跨系统写入、身份权限、敏感数据、资金、不可逆迁移或外部合同尚不确定的变更。在标准方案之上，必须补齐状态机、并发与未知结果、撤权对账、安全威胁、可观测性、迁移回滚和上线闸门。

不是每个方案都要覆盖全部维度。对不适用的维度直接略过；对已判定不存在的风险不预造机制。

## 动作协议

### 1. 锁定问题与现行真相

1. 用一段话写清现状、问题、目标和方案成功后的变化。
2. 明确范围和非目标，防止方案在推演中暗中改写需求。
3. 读当前有效的 PRD、架构、契约、源码和项目约定；标记历史文档、废弃方案和尚未生效的提案，不把它们当成现行真相。
4. 如果上位产品边界未定，或当前系统是否应承担该问题尚未决策，停在边界对齐，不提前展开字段和 API。

### 2. 建立认知台账

关键信息必须区分：

- **已验证事实**：有源码、现行契约、实验或外部权威证据支持。
- **用户已决策**：由用户明确拍板，变更时需要重新对齐。
- **方案建议**：我基于当前证据提出的倾向，不冒充用户决策。
- **暂定假设**：为了继续推演暂时采用，必须同时记录不成立时的影响。
- **待确认问题**：当前缺少证据或决策，标明责任方、影响范围和是否阻断。

事实与当前实现可以主动查证；产品取舍、风险接受和方向选择由用户拍板。

### 3. 建模对象、边界与不变量

1. 列出核心对象、角色、系统和外部依赖。
2. 对每个核心对象回答：它的稳定身份是什么，谁是唯一事实来源，谁管理生命周期，能否复用、合并、迁移、删除。
3. 明确系统职责、数据所有权、信任边界和不允许跨越的责任。如果两处事实冲突，必须能回答最终以哪一处为准。
4. 将关键结论收成可判定不变量，例如唯一性、可进入条件、不可逆状态、权限交集和敏感信息禁止流向。
5. 不变量必须继续映射为数据约束、状态迁移、接口行为、授权条件或验收证据中的至少一种，不停在“注意一致性”“保证安全”这类口号。

### 4. 推演流程、异常与恢复

1. 先写清主流程，再沿每个有状态变更或外部副作用的步骤向下推演。
2. 根据实际风险检查重复、并发、超时、断连、局部成功、远端成功但本地失败、撤销、重装和外部变更。
3. 对每个外部写操作说明：是否幂等，是否可查询，是否可撤销，何时允许重试，结果未知时如何阻止第二次副作用并收敛事实。
4. 有多步生命周期时使用状态机表达；只有局部成功/失败时，使用简短错误表即可，不为简单流程预造状态机。
5. 安全、撤权、对账和人工介入应与真实威胁和外部能力匹配，不以“先上线再说”淹没风险，也不对不存在的故障加机制。

### 5. 转换为工程设计

只在问题边界和不变量稳定后，再选择需要的实现载体：

- 模块职责和依赖方向。
- 数据模型、唯一约束和不可变字段。
- 状态机与并发控制。
- API 契约、错误语义和幂等规则。
- 身份、权限、信任边界和敏感数据流向。
- 审计、指标、告警和运维操作。
- 迁移、兼容、回滚和降级。

只展开会改变决策、实现或验收的内容。字段、接口和异常细节不得早于上位边界和外部合同被过早写死。

### 6. 形成差距和实施路径

1. 对照当前真实实现，将所需能力分为：直接复用、需要扩展、必须新增、明确禁止复用、依赖外部条件。
2. 实施顺序由依赖、风险前置、最小可验证闭环和可回滚性决定，不按方案文档的章节顺序拆任务。
3. 每个阶段写清进入条件、范围与非范围、产出、验收证据、退出条件和未满足时的处置。
4. 尚未关闭的外部问题标明责任方和阻断范围；可以先做 fake、contract test 或本地状态机时，明确它们不构成生产能力已具备的证据。

### 7. 建立验收与拍板点

1. 验收标准覆盖正常路径、关键边界、失败恢复和安全不变量，每条都必须可观察、可判定。
2. 为每个上线闸门写明证据、责任方和未满足时允许做什么、禁止做什么。
3. 产品取舍、风险接受、方向选择和会改变整体范围的点单独递给用户拍板；不用技术细节淹没决策。
4. 方案未经用户拍板时，可以作为建议继续迭代，不直接将其当成 TODO 实施基线。

## 产出形态

普通方案直接在对话中给出。只有用户要求保存、转交、作为后续实施依据，或方案本身是交付物时，才写入 `projects/outbox/solutions/`。不为每次讨论自动建文档或台账。

产出根据深度按需选择，不强制齐备章节：

```md
# <方案名称>

## 判断与推荐
## 事实、决策、假设与未知
## 问题、目标与非目标
## 对象、责任与事实所有权
## 核心不变量
## 方案与取舍
## 流程、状态与失败恢复
## 安全、迁移与可观测性
## 现状差距与分阶段实施
## 开放问题与上线闸门
## 验收标准
## 需要你拍板
```

保存的方案应在正文中标明状态、日期、适用范围和权威边界。历史、废弃或被新方案取代时，必须在文档顶部显式降级，不让旧结论继续冒充现行真相。

## 退出检查

方案进入拍板或实施前，核对：

- 当前有效的上位产品和系统边界已识别，历史方案没有被当成现行依据。
- 已验证事实、用户决策、方案建议、暂定假设和待确认问题没有混写。
- 核心对象有稳定身份、唯一事实来源和生命周期责任方。
- 两个系统的事实冲突时，能判定最终以谁为准。
- 关键结论已收成不变量，并落到至少一种可验证载体。
- 每个外部副作用的重复、并发、局部成功和未知结果已按实际风险处理。
- 安全、撤权、对账、迁移、回滚和观测性的深度与真实风险匹配。
- 实施路径来自现状差距和依赖，不是对方案章节的机械拆分。
- 开放问题有责任方、影响和阻断范围，没有用猜测填平。
- 验收标准可观察、可判定，能证明关键不变量而不只是功能主路径。
- 需要用户拍板的产品取舍、风险接受和方向选择已单独列出。

## 红线

- 不替用户拍产品、风险接受或架构方向的板。
- 不根据关键词或固定章节判断方案类型和深度。
- 不把假设、建议、历史提案或外部口头信息写成已验证事实。
- 不用一份宏大文档掩盖上位产品边界未定。
- 不在外部合同和责任边界尚未明确时过早写死字段、API 和实现细节。
- 不为低风险任务套完整方案流程，也不因方案庞大而省略高风险闭环。
- 不把方案文档当成完成证据，也不用它代替 PRD 或 TODO 的事实和状态。
- 方案未拍板或关键闸门未满足时，不据此进入生产实施。
